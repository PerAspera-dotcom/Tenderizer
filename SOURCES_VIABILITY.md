## What changed vs. the CR's own preliminary hypotheses

- **UK**: confirmed green via FTS specifically (not MyTenders/MOD-specific portals), including defence coverage — matches the CR's own preferred path.
- **Canada**: confirmed green, exactly as hypothesized.
- **TenderNed**: confirmed green, exactly as hypothesized (CC0, not just "likely").
- **Australia**: the CR's "amber" guess undersold the problem — this is a real legal blocker on the exact data wanted (ATM material), not a wait-and-see. Marking red rather than amber so it doesn't quietly become a default "build it anyway, it's technically public" later.
- **Saudi**: better news than the CR's premise assumed — a real API program exists at `apiportal.etimad.sa`, not just a login-walled site. Still not confirmed to cover tender-listing data, so still amber, but the next step is "register and look at the product catalog," not "write off this market."
- **UK Contracts Finder**: better news than hypothesized — the "needs a Sid4Gov account" read came from the generic developer docs, which only describe the notice-*submission* flow. The actual read/search endpoint is confirmed live with zero auth. Upgraded straight to green and built.
- **Singapore (GeBIZ)**: worse news than hypothesized — robots.txt looking permissive turned out not to matter, because the listing page is a stateful JSF app that returns no data to a plain fetch at all (not a ToS question, a technical one). Downgraded from amber to red.
- **Malaysia / Philippines**: stayed amber as hypothesized — neither could be upgraded or downgraded with page-fetch-level evidence; each needs a real-browser probe (both gave anti-bot/error signals to a plain fetch) before any build decision.

## Built (CR-011 §4, this pass)

All four confirmed-green sources now have working, tested connectors — `connectors/find_a_tender.py`, `connectors/contracts_finder.py`, `connectors/canadabuys.py`, `connectors/tenderned.py` (+ matching `normalize.py` functions, `tests/test_56_new_sources.py`, wired into `run.py`/`config/portals.yaml`/`api.py`'s Portal Health panel). All four ship `enabled: false` — connector-complete, pending a business go-live decision, same gate Bekanntmachungsservice went through in CR-010 before its own go-live.

- **UK — Find a Tender Service**: public OCDS API, OGL-licensed, English, includes MOD/defence, CPV-native (no mapping needed).
- **UK — Contracts Finder**: same OCDS/OGL/English/CPV-native shape, a separate (older, still-active, below-FTS-threshold) system — registered as its own portal, not merged into FTS.
- **Canada — CanadaBuys**: daily CSV pull, OGL-licensed, English. No CPV mapping built (see below) — keyword-matched only.
- **TenderNed**: CC0, Dutch (goes through DeepL), CPV-native. Uses a confirmed-open JSON endpoint, not the credential-gated one the generic docs describe — no email/credential step actually needed for this build.

**CanadaBuys' classification gap, stated plainly**: CanadaBuys uses GSIN/UNSPSC, not CPV, and no verified GSIN/UNSPSC→CPV crosswalk was available to build against — inventing one risked silently wrong matches, which seemed worse than relying on keyword matching alone (what this build does; `cpv_codes` is always `[]` for this source, so `match_source` is honestly tagged "keyword" or absent, never a false "cpv"/"both"). Revisit if a verified crosswalk turns up.
